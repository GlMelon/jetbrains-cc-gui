## 1. 总体设计

### 当前问题

现在已经有 `HistoryProviderAdapter`，但流程还分散在多个 service 里：

```text
HistoryLoadService
HistoryDeleteService
HistoryMessageInjector
HistoryProviderRegistry
ClaudeHistoryProviderAdapter
CodexHistoryProviderAdapter
OpenCodeHistoryProviderAdapter
```

其中：

- 历史列表加载在 `HistoryLoadService`
- 单删 / 批删在 `HistoryDeleteService`
- 刷新逻辑分散在删除后、深度搜索后
- provider 差异已经适配了一部分，但上层流程还不够集中
- OpenCode 因为 DB 失败时可能返回空字符串，所以 adapter 里单独做了空结果归一化

### 改造目标

抽出一个统一流程层：

```text
HistoryWorkflowService
```

它只关心“历史业务动作”，不关心底层是 JSONL 还是 SQLite。

统一动作：

```java
// 对外
refresh(provider)                              // load + enhance + dispatch
deleteOne(provider, sessionId)                 // delete + cleanup + clearCache + refresh
deleteMany(provider, sessionIds)               // N×(delete + cleanup) + 1×clearCache + 1×refresh
// package-private，供 deleteMany 组合
deleteWithoutRefresh(provider, sessionId)      // delete + cleanup，不 clearCache、不 refresh
clearCache(provider)
```

> 📌 审查补充（修订 1/2）：**不纳入 `loadMessages`**。`load_session` 实际链路是 `HistoryActionHandlers.handleLoadSession → HistoryMessageInjector.handleLoadSession → SessionLoadCallback.onLoadSession(...)`，真正的 `adapter.loadMessages` 消费方在 callback 实现（history 包之外）。workflow 接管 `loadMessages` 没有调用方，**维持 callback 现状**。

provider 差异仍然留在 adapter：

```java
ClaudeHistoryProviderAdapter
CodexHistoryProviderAdapter
OpenCodeHistoryProviderAdapter
```

# Task 3：新增统一历史工作流服务

## 目标

新增：

```text
HistoryWorkflowService
```

它负责统一编排：

```java
void refresh(String provider)
HistoryDeleteResult deleteOne(String provider, String sessionId)
HistoryBatchDeleteResult deleteMany(String provider, List<String> sessionIds)
// package-private，供 deleteMany 组合
HistoryDeleteResult deleteWithoutRefresh(String provider, String sessionId)
void clearCache(String provider)
```

底层仍调用：

```java
historyProviderRegistry.adapter(provider)
```

> 📌 审查补充（修订 1）：**不接管 `loadMessages`**，理由见 §1。保持 `load_session` 现有 callback 链路不动。

## 新增文件

```text
src/main/java/com/github/claudecodegui/handler/history/HistoryWorkflowService.java
```

建议结构：

```java
final class HistoryWorkflowService {
    private final HandlerContext context;
    private final HistoryProviderRegistry providerRegistry;
    private final HistoryProjectPathResolver projectPathResolver;
    private final HistorySessionsJsonEnhancer sessionsJsonEnhancer;
    private final HistoryLoadService historyLoadService;
    private final NodeJsServiceCaller nodeJsServiceCaller;

    /**
     * 同步逻辑：load → enhance → dispatch。
     * 📌 审查补充（修订 7/8）：refresh 本身同步，由调用方（HistoryActionHandlers）
     * 负责 CompletableFuture.runAsync 包裹，避免阻塞 EDT（adapter 读 JSONL / SQLite 是 IO）。
     * 异常在此捕获并下发错误 JSON，不向外逃逸（对齐现状 HistoryLoadService 的 try/catch + setHistoryData({success:false})）。
     */
    void refresh(String provider) {
        String projectPath = projectPathResolver.resolve(context);
        if (projectPath == null) {
            return;
        }
        try {
            HistoryProviderAdapter adapter = providerRegistry.adapter(provider);
            String rawJson = adapter.loadSessionsJson(projectPath);
            String enhancedJson = sessionsJsonEnhancer.enhance(provider, rawJson);
            historyLoadService.dispatchHistoryData(enhancedJson);
        } catch (Exception e) {
            LOG.warn("[HistoryWorkflow] refresh failed: " + e.getMessage(), e);
            historyLoadService.dispatchHistoryDataError(e.getMessage());
        }
    }

    HistoryDeleteResult deleteOne(String provider, String sessionId) {
        HistoryDeleteResult result = deleteWithoutRefresh(provider, sessionId);
        clearCache(provider);
        refresh(provider);
        return result;
    }

    HistoryBatchDeleteResult deleteMany(String provider, List<String> sessionIds) {
        int mainDeleted = 0;
        int agentFilesDeleted = 0;
        for (String sessionId : sessionIds) {
            try {
                HistoryDeleteResult r = deleteWithoutRefresh(provider, sessionId);
                if (r.mainDeleted()) mainDeleted++;
                agentFilesDeleted += r.agentFilesDeleted();
            } catch (Exception e) {
                LOG.error("[HistoryWorkflow] batch delete single failed: " + sessionId, e);
            }
        }
        clearCache(provider);   // 批删：N delete + 1 clearCache + 1 refresh
        refresh(provider);
        return new HistoryBatchDeleteResult(sessionIds.size(), mainDeleted, agentFilesDeleted);
    }

    /**
     * 📌 审查补充（修订 2）：package-private，供 deleteMany 组合，
     * 避免「每删一个就 clearCache / refresh」（批删只末尾做一次）。
     */
    HistoryDeleteResult deleteWithoutRefresh(String provider, String sessionId) {
        String projectPath = projectPathResolver.resolve(context);
        if (projectPath == null) {
            return HistoryDeleteResult.none();
        }
        HistoryDeleteResult result = providerRegistry.adapter(provider)
                .deleteSession(sessionId, projectPath);
        if (result.mainDeleted()) {
            cleanupSessionMetadata(sessionId);
        }
        cleanupSessionAttachments(provider, sessionId);
        return result;
    }

    void clearCache(String provider) {
        String projectPath = projectPathResolver.resolve(context);
        if (projectPath == null) return;
        try {
            providerRegistry.adapter(provider).clearCache(projectPath);
        } catch (Exception e) {
            LOG.warn("[HistoryWorkflow] clearCache failed: " + e.getMessage());
        }
    }
}
```

注意：这一步需要先把 `HistoryLoadService` 的前端注入逻辑抽成 package-private 方法：

```java
void dispatchHistoryData(String finalJson)        // 成功下发（Base64 注入 window.setHistoryData）
void dispatchHistoryDataError(String message)     // 📌 审查补充（修订 8）：失败下发 {success:false,error}
```

这样 `HistoryWorkflowService` 可以复用已有下发逻辑，不直接拼 JS（含错误兜底，对齐现状 `HistoryLoadService` 第 102–112 行）。

# Task 4：收敛 HistoryLoadService

## 目标

`HistoryLoadService` 不再负责：

```text
provider 选择
project path 解析
favorites/titles 增强
deep search clear cache 编排
```

它只保留：

```text
把已准备好的 history JSON 下发给前端
```

## 修改文件

```text
src/main/java/com/github/claudecodegui/handler/history/HistoryLoadService.java
```

建议拆出：

```java
void dispatchHistoryData(String finalJson)
```

保留原 Base64 注入逻辑。

原来的：

```java
void handleLoadHistoryData(String provider)
```

> 📌 审查补充（修订 3）：**删除原「改成委托 `workflow.refresh`」方案**——它会让 `HistoryLoadService` 反向依赖 `HistoryWorkflowService`，而 workflow 又依赖 `LoadService.dispatchHistoryData`，形成循环（与本节原描述自相矛盾）。

**定死单向依赖**（与「风险点 1」合并后的最终方案）：

```
HistoryActionHandlers ──► HistoryWorkflowService ──► HistoryLoadService.dispatchHistoryData(/Error)
```

即：

- `HistoryWorkflowService` 单向依赖 `HistoryLoadService` 的 package-private `dispatchHistoryData` / `dispatchHistoryDataError`；
- `HistoryLoadService` **不反向依赖** workflow 或 handlers；
- `HistoryActionHandlers.handleLoadHistoryData` 直接调 `workflow.refresh(currentProvider)`，**由 Handlers 负责 `CompletableFuture.runAsync` 包裹**（见 Task 3 线程模型），不再经过 `historyLoadService.handleLoadHistoryData`；
- `HistoryLoadService` 收敛后只保留 `dispatchHistoryData` / `dispatchHistoryDataError`（Base64 注入逻辑）；原 `handleLoadHistoryData` / `handleDeepSearchHistory` / `enhanceHistoryWithFavorites` / `enhanceHistoryWithTitles` 逻辑迁出（分别去 Handlers→workflow / workflow / enhancer）。

这样 `HistoryLoadService` 仅剩「把准备好的 JSON 下发给前端」一职，与「改造目标」一致，且无循环依赖。

HistoryBatchDeleteResult deleteSessions(String provider, List<String> sessionIds) {
    int mainDeleted = 0;
    int agentFilesDeleted = 0;

    for (String sessionId : sessionIds) {
        HistoryDeleteResult result = workflowService.deleteWithoutRefresh(provider, sessionId);

        if (result.mainDeleted()) {

# 风险点

## 1. 循环依赖

不要让：

```text
HistoryWorkflowService -> HistoryLoadService
HistoryLoadService -> HistoryWorkflowService
```

形成强循环。

推荐：

```text
HistoryActionHandlers
  -> HistoryWorkflowService
  -> HistoryFrontendDispatchService
```

如果要更干净，可以把前端注入逻辑也单独抽成：

```text
HistoryFrontendDispatchService
```

但第一阶段可以先不抽，避免改动过大。

## 2. OpenCode 删除语义

OpenCode 是软删除：

```sql
update session set time_archived = ?
```

不要改成文件删除。

## 3. 批量删除性能

批量删除必须：

```text
N 次 delete
1 次 clearCache
1 次 refresh
```

不要每删一个刷新一次。

## 4. provider fallback

不要出现 unknown provider fallback 到 Claude。

当前 `HistoryProviderRegistry` 已有测试要求 unknown provider 抛异常，这个行为要保留。

## 5. currentProvider 共享可变状态并发

> 📌 审查补充（补充 9）：`HistoryActionHandlers.currentProvider` 是实例字段，被 load / delete / deepsearch 各 handler 共享读写，且切换 handler 会覆盖它；而 delete 在 `CompletableFuture.runAsync` 内读取。快速切换 provider 时，异步删除可能读到被覆盖的 provider。

- 该隐患**现状就存在，统一化不会消除它**；
- **附带收益**：workflow 化后 provider 显式传参，各 handler 可逐步消除对 `currentProvider` 字段的依赖（本次不强制，作为后续清理方向）；
- 本次至少保证：delete / deleteMany 异步任务启动时**捕获 provider 快照**传入，而非在 `runAsync` 内读字段。
